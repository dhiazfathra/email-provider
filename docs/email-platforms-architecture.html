Two email platforms — architecture sketch

A) Mailbox hosting (Gmail/Zoho competitor)  ·  B) Transactional/bulk send API (SendGrid/Mailgun competitor)

module boundary seam / adapter point deliverability risk edge deep module (own most complexity)

A) Mailbox hosting service

Speculative — high build cost

Full mail server as the deep module. You do not implement SMTP/IMAP/spam filtering yourself — Stalwart or Mailcow is the deep module, and your job is provisioning, billing, and the webmail seam on top of it.

Wins if built this way

  • Leverage: one deep mail-server module, N mailbox tenants
  • Locality: spam/DKIM/DMARC logic stays inside the deep module, not scattered across your Go layer
  • Seam: webmail and provisioning stay swappable adapters over Stalwart's JMAP/REST surface

Where it leaks

  • Deliverability reputation is external state (Google/Microsoft trust) — no module boundary contains it
  • New domains inherit no reputation; smart-host relay is a forced seam early on
ADR candidate: adopt Stalwart (single Rust binary, JMAP-native, S3 backend) over Postfix+Dovecot+SOGo — fewer seams to operate, closer fit to a containerized Go-centric stack.

B) Transactional / bulk email API

Strong — fits existing stack

Send path as an outbox-pattern pipeline: API accepts and queues, workers own delivery. This is the same shape as the outbox pattern already in use elsewhere — the deep module here is the MTA + retry/bounce handling, not the API.

    participant MTA as MTA (Postfix / Haraka)
    participant CH as ClickHouse\n(events: sent, opened, clicked, bounced)
    participant Hook as Tenant webhook

    Tenant->>API: POST /v2/send (idempotency_key, template, payload)
    API->>PG: validate tenant, template, suppression list
    API->>Q: enqueue outbox event
    API-->>Tenant: 202 accepted
    Q->>W: deliver event
    W->>MTA: SMTP send (DKIM signed)
    MTA-->>W: accepted / bounced
    W->>CH: record delivery event
    MTA-->>CH: bounce / complaint webhook
    CH->>Hook: forward event (open/click/bounce)

Wins if built this way

  • Leverage: outbox pattern reused verbatim from existing architecture
  • Locality: suppression enforcement lives at accept-time, not scattered across workers
  • Interface shrinks: tenants see one POST /send; queueing, retries, IP pooling all internal

Where it leaks

  • MTA reputation is shared external state again — same leak shape as (A), smaller surface
  • Feedback loop (bounce → suppression) must be synchronous enough to block re-sends, or it's a seam that silently drifts
ADR candidate: suppression-list check happens in the accept path (A2), not the worker — keeps compliance logic local to one seam instead of duplicated per worker.

Build order

Start with B) transactional email API. It validates the deliverability infrastructure — DKIM signing, IP warmup, bounce handling, ClickHouse event pipeline — that A) needs anyway, using an architecture that's a direct match for the outbox pattern already in place. A) then becomes: adopt Stalwart, put the same provisioning discipline in front of it, and reuse the reputation-management work from B.
